# Codex 두 패널 개발 시작 프롬프트

같은 Capability Manager 프로젝트를 연 Herdr의 Codex 패널 두 개를 준비한다. 아래 블록 전체를 **한쪽 패널에만** 붙여 넣는다. 이 패널이 구현·통합을 맡고 실제 발견한 다른 패널에 검토 요청을 보낸다. 패널 ID를 미리 기입할 필요가 없다.

```text
Capability Manager 개발을 시작해줘. 먼저 적용되는 상위 지침과 루트 AGENTS.md를 읽어줘.
AGENTS.md가 없으면 문서의 합의된 규칙으로 먼저 작성하고, 있으면 보존하면서 필요한 부분을 보완해줘.
다른 패널에 AGENTS.md와 개발 계약을 첫 검토로 보내고, 수정·재검토를 마친 뒤 제품 구현에 들어가줘.
현재 프로젝트의 docx/README.md에서 문서 세트를 읽고,
04-implementation-plan.md의 P00부터 P09까지 실제 구현·테스트·통합을 진행해줘.
이번 요청은 계획 작성만이 아니라 제품 코드, RPM, 단위 테스트 프레임워크와 기기 검증 도구 구현 요청이야.

개발 저장소는 https://github.com/hjhun/capability-manager 이고 라이선스는 Apache-2.0이야.
이 저장소에 개발 과정의 커밋을 만들고 push하면서 진행하는 것을 승인해.
시작할 때 현재 checkout·remote·branch와 원격의 기존 이력을 확인하고, 원격 LICENSE와 초기 커밋을 보존해줘.
현재 디렉터리가 Git 저장소가 아니면 기존 문서를 보존하면서 원격 이력을 기반으로 작업할 checkout을 마련해줘.
다른 remote를 임의로 바꾸거나 독립된 root 이력을 만들어 원격을 덮어쓰지 마.
Git 작업은 구현·통합 담당인 너만 수행하고 검토 패널은 동시에 stage/commit/push하지 않게 해줘.
git-commit 스킬을 적용하고, 리뷰와 해당 범위 검증을 마친 의미 있는 작업 단위마다 영어 메시지로 커밋한 뒤 push해줘.
최종 개발 완료 때까지 커밋·push를 미루지 말고, 단계가 크면 검증 가능한 작은 단위로 나눠줘.
통상적인 커밋·push마다 다시 승인을 묻지 마. force push나 기존 공개 이력 재작성은 하지 마.
원격 변경은 fetch 후 보존하여 통합하고, 보호 브랜치 정책이 있으면 작업 브랜치로 push해줘.
Apache-2.0 LICENSE를 유지하고 신규 자체 소스·RPM의 라이선스 표기를 맞춰줘.
제3자 코드의 기존 저작권·라이선스 고지는 보존하고, 빌드 산출물·원시 기기 로그·비밀값은 커밋에서 제외해줘.

너는 구현·통합 담당이고, 내가 준비한 다른 Codex 패널은 독립 검토 담당으로 사용해줘.
Herdr 스킬을 읽고 HERDR_ENV=1인지 확인한 뒤 설치된 CLI help와 실제 agent/pane 목록에서
현재 패널 및 같은 프로젝트의 다른 Codex 패널을 찾아줘. 예시 ID를 추측하거나 새 패널을 만들지 마.
다른 대상이 여러 개면 대상만 확인해줘. Herdr 밖이면 그 사실을 알려주고 외부 세션을 제어하지 마.
두 패널 간 작업 요청·검토·회신을 승인해. 06-herdr-workflow.md에 따라 상대에게 문서 위치,
역할, 구체적인 검토 범위와 실제 회신 대상을 전달하고, 상호 요청에는 --wait를 사용하지 마.
상대의 검토를 받으면서 독립 작업을 계속하고, 같은 파일은 동시에 수정하지 않도록 소유권을 정해줘.
검토가 필요한 변경마다 작업 ID·검토 revision·파일/diff·검증 근거·회신 대상을 포함해 상대에게 보내줘.
검토자는 ACCEPTED/CHANGES_REQUESTED/BLOCKED와 근거를 회신하고,
수정 요청을 받은 쪽은 반영·영향 범위 재검증 후 변경된 revision을 상대 패널에 다시 보내 재검토받아줘.
질문·추가 증거·후속 검토가 필요하면 두 패널이 서로 구체적인 요청을 다시 보내며 이 과정을 반복해줘.
수정했다고 자체 종결하지 말고 해당 revision의 검토 수락까지 확인해줘. 응답이 없다는 건 수락이 아니야.
검토 수락·필요 검증 후 commit/push하고, 다음 작업과 다음 검토 요청을 이어서 전달해줘.
사용자가 패널 사이에서 메시지를 중계하거나 매번 계속하라고 말할 필요 없이 진행해줘.

최신 계약은 01-requirements.md와 03-api-contracts.md, 미정 사항은 07-decisions-and-open-items.md야.
예전 docs/design-discussion.md의 상충하는 내용을 되살리지 마.
C++20 구현, capmgr_ C API, RPM, TIDL, Watcher 스타일을 지켜줘.
client create는 권한과 readonly DB 접근까지, 리소스 mount는 목적지를 받는 명시 remount 호출이야.
Skill/App Skill/CLI는 parser가 직접 DB를 갱신하고 MIC에서 AMD 없이 동작해야 해.
Action은 기존 DB에서 import하고 변경 반영 commit 후 client에 알리며, 조회마다 IPC하지 마.
Skill은 경로로 제공하고, CLI는 --json 다음 전체 JSON-RPC 요청을 단일 argv로 전달해.
Action 공개 필드, provider ID 목록/default ID, Entity, App Skill 동명 허용 등 합의된 계약을 유지해줘.

기존 AUL의 Google Test/Google Mock 선례를 확인해 빌드 단계 테스트를 처음부터 구성해줘.
C consumer compile/link, 실제 SQLite 테스트, 에뮬레이터·실기기 integration/smoke/performance 도구도 만들어줘.
연결된 에뮬레이터와 내부 build tool·의존성을 확인해서 그 안에서 개발·검증할 경로를 마련해줘.
문서에 적힌 PATH 미발견을 설치 부재로 단정하지 말고 실제 환경에서 확인해줘.
32비트 ABI와 크기 계산은 처음부터 고려하되 실제 ARMv7l 빌드는 모든 기능 개발과 주 환경 검증이 끝난
P09에서만 수행해줘. x86 테스트, ARM 빌드, ARM 기기 실행 결과를 구분해줘.

기술 선택은 근거와 검토 결과로 자율 해결하고 매 단계 계속할지 묻지 마.
PATH-01처럼 마지막 사용자 표현이 모호한 제품 의미만 짧게 확인하고, 독립 작업은 계속해줘.
기존 작업과 운영 데이터를 보존하고, 무관한 저장소는 수정하거나 push하지 마.
필요한 추가 권한·인증 또는 환경 차단이 있으면 정확한 원인과 막히는 단계만 알려줘.

각 단계의 산출물·실행 명령·exit status·테스트 결과·기기 증거를 08-progress.md에 연결해줘.
커밋 ID·branch·push 결과도 기록하고, 원격 ref에 해당 커밋이 반영됐는지 확인해줘.
인증이나 네트워크 문제로 push가 실패하면 로컬 커밋을 보존하고 미전송 상태를 정확히 보고해줘.
검토 담당에게 실패 경로와 실제 증거까지 검토받고, 수정 사항을 반영해 다음 단계로 진행해줘.
패널 idle/done이나 빌드 성공만으로 전체 완료라고 하지 마. 필수 검증 미실행은 NOT_RUN/BLOCKED로 남겨줘.
최종적으로 R01–R18 구현과 검증, 에뮬레이터/실기기 결과, ARMv7l 최종 빌드 결과 및 남은 제한을 보고해줘.
이제 문서와 현재 상태를 확인하고 다른 패널에 첫 검토 요청을 보낸 뒤 실제 개발을 시작해줘.
```

문서 작성 시점에는 위 프롬프트를 다른 패널에 보내지 않았다. 실행 환경·패널·기기 상태는 시작할 때 다시 확인한다.
